Introduction

Systemd is a default Linux-based software that manages how, when, what, and where Linux services run. It is a powerful tool that allows users to have greater control over the operating system, especially when there are multiple services that need to be managed. More specifically, systemd lets users decide which processes should run at startup, these are known as init systems. Another common use case is scheduling recurring tasks, for example, running a specific program every five seconds.

There are other tools such as cron, Jenkins, and Rundeck that can perform certain automation or scheduling tasks similar to systemd. However, systemd provides a more comprehensive and integrated approach, covering almost every aspect of service management, automation, and timed execution. Therefore, it is often preferred in professional Linux environments, especially for stable and reliable data logging systems.

Systemd was initiated by Red Hat engineers Lennart Poettering and Kay Sievers in 2010 as a replacement for the older System V init. Their goal was to modernize the Linux initialization process, improving efficiency and flexibility. Poettering’s blog post, titled Rethinking PID 1, introduced the first experimental version of systemd and outlined its vision to enhance dependency handling, enable more parallel process execution during boot, and reduce the computational overhead associated with shell scripting.

In May 2011, Fedora Linux became the first major distribution to adopt systemd as its default init system, replacing Upstart. This was followed by Arch Linux in 2012, after developers agreed that systemd was faster, more feature-rich, and easier to maintain than sysvinit. Despite some controversy within the open-source community, particularly regarding its complexity, reliance on D-Bus, and its binary log format—many maintainers viewed these as advantages that improved performance and maintainability.

Between 2013 and 2014, the debate over adopting systemd reached the Debian community, where it became a major topic of discussion. After much deliberation, Debian decided to make systemd the default init system in Debian 8. The decision led to several developer resignations due to the heated nature of the debate, but eventually, other major distributions such as Ubuntu also followed suit, replacing Upstart with systemd. Since then, systemd has continued to evolve, introducing new components such as machinectl shell for login management, though it has also faced occasional criticism due to security vulnerabilities discovered in later years.

Overall, systemd represents a significant evolution in Linux system management combining speed, automation, and process control into a unified framework that has become the standard across most modern Linux distributions.

Systemd has several advantages:

  • Fast and parallelized boot process
  • Unified management of services, logs, and dependencies
  • Powerful process tracking and restart capabilities
  • Integrated logging via journalctl
  • Improved security and isolation through cgroups and namespaces

Create Your First Service in systemd

In this section, we will demonstrate how to create your own service so that your Linux system can recognize and automatically manage it. All user-defined services are stored in the directory /etc/systemd/system/. To create a new service, start by creating a service file using the command below: 

sudo nano /etc/systemd/system/x_logger.service

After creating the file, you can define your service by adding the following configuration: 

[Unit]
Description=X Data Logger
After=network.target

[Service]
Type=simple
User=utar-mini-pc
WorkingDirectory=/path/to/your/Modbus_loggers
ExecStart=/path/to/your/python/environment/python modbus_logger.py configs/x_conf.json
Restart=always
RestartSec=2

[Install]
WantedBy=multi-user.target

Let’s go through each section and attribute to understand their purpose:

  • [Unit]: Defines metadata and dependencies of the service.
    • Description – A short summary of what the service does.
    • After – Specifies which system target or service must start before this one. For example, After=network.target ensures the network is ready before this service starts.
  • [Service]: Defines how the service behaves when started or stopped.
    • Type=simple – Indicates that the service runs continuously in the foreground.
    • User – Specifies which user account runs the service. It is good practice not to run services as root for security reasons.
    • WorkingDirectory – Sets the directory where the service will execute. This is often where your scripts or configuration files are located.
    • ExecStart – Defines the command to run when the service starts. In this example, it launches your Python logger script with the specified configuration file.
    • Restart – Determines whether the service should automatically restart if it stops or fails. Setting it to always ensures high availability.
    • RestartSec – Specifies how many seconds to wait before restarting the service after a failure.
  • [Install]: Defines how the service integrates with the system.
    • WantedBy – Specifies the target under which the service should be enabled. multi-user.target means the service will start automatically during normal multi-user system boot.

Once you’ve saved the file, reload the systemd daemon so that it recognizes the new service: 

sudo systemctl daemon-reload

You can then start and enable the service using the following commands: 

sudo systemctl start x_logger.service
sudo systemctl status x_logger.service
sudo systemctl enable x_logger.service

With this setup, your custom data logging service will automatically start on boot and restart if it encounters an error, ensuring continuous and reliable operation.

Tail the Service Log

You can monitor your service’s real-time output using journalctl. The following command continuously displays log entries for your service: 

journalctl -u x_logger.service -f -o cat

The -u flag specifies the unit (service) name, -f follows the log (like tail -f), and -o cat prints only the log message, without metadata.

Stop and Remove the Service

To stop and completely remove your service from the system, run the following commands in order: 

sudo systemctl stop x_logger.service
sudo systemctl disable x_logger.service
sudo rm /etc/systemd/system/x_logger.service
sudo systemctl daemon-reload

Finally, verify that the service has been removed: 

systemctl status x_logger.service

If the removal is successful, systemd will respond with a message indicating that the service could not be found.
